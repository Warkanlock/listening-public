# Extension boundary review

This review covers the server, manager, clients, installation, and release configuration at the 2.0.8 baseline. It also records the catalog-hosting change made in this sweep.

## How acquisition and sharing work

The room selects a search extension and a fetch extension independently. The signed catalog declares each extension's capabilities, candidate namespaces, and image digest. The manager starts the worker and exposes the declared methods over its socket. A search response contains opaque candidate IDs. The fetcher returns a completed file in staging. Core verifies the bytes and owns playback eligibility, retry, storage, and queue state. [Engine contract](../backend/downloads/engine_contract.py) · [Engine manager](../backend/system/engine_fleet.py) · [Verification](../backend/downloads/verification.py)

A sharing extension controls its own network protocol and account settings. The host operator chooses which directory is available, and the manager mounts the selected folder read-only. The default server image can import and play audio with no extensions installed. The optional Compose override adds the manager socket and staging mounts. [Extension protocol](../examples/engines/README.md) · [Core image](../Dockerfile) · [Compose override](../packaging/compose.engines.yaml)

Android renders extension inventory from registered IDs, versions, and readiness. Its legacy status covers older room servers. The server checks capabilities. Mac and iPad use the web interface, which reads those capabilities to display extension controls. [Android extension inventory](../clients/android/app/src/main/java/music/listening/room/RoomExtensions.kt) · [Web extension settings](../frontend/react/src/views/settings/ExtensionsPanel.tsx)

## Remaining coupling

| Area | What the review found | Implication |
| --- | --- | --- |
| Catalog delivery | The manager could read a local signed catalog. Its built-in remote transport required GitHub Releases. This sweep adds direct HTTPS hosting for the signed catalog pair. Web Settings still links to the project's default directory of plugins. | A publisher can choose its own host or registry while keeping signed metadata, digest pins, and offline startup. [Catalog transport](../backend/system/engine_repository.py) · [Manager setup](download-engines.md#set-up-the-manager-on-a-linux-docker-host) |
| Recording identity | The worker receives the room's internal ID, text, duration, and format preferences. The payload omits public identifiers such as an ISRC. Exact-edition requests use MusicBrainz identifiers to activate stricter verification. | Adding namespaced public identifiers needs a compatibility check for existing workers and persisted copy selections. Limited identity hints must preserve title, duration, codec, and bitrate checks. [Recording payload](../backend/downloads/engine_contract.py) · [Saved copies](../backend/downloads/requests_store.py) · [Verification](../backend/downloads/verification.py) |
| Playlist identity and links | The list reader recognizes explicit Spotify playlist identifiers. The catalog rebuild reads Spotify mirror state, and playlist edit and backup code include the connection. The generic tracks API also supports the `spotify=1` option and `spotify_url` fields. | A generic playlist identity rule needs to account for automatic grouping of equal IDs and existing stored links. Move provider normalization behind its adapter before widening accepted IDs. [List protocol](../backend/library/library_protocol.py) · [Playlist grouping](../backend/library/playlist_links.py) · [Catalog rebuild](../backend/runner.py) · [Track API](../backend/server.py) · [Snapshots](../backend/catalog/collection_snapshot.py) |
| Radio | The Extensions screen lists built-in Radio providers alongside installed extensions. The server still owns their settings and playback behavior. New rooms leave them disabled. Older rooms preserve their previous Radio access. | Give built-in sources an explicit label if the screen continues to list them together. A future Radio extension needs a playback contract that accounts for live streams and per-device state. [Radio settings](../backend/playback/radio.py) · [Extension settings](../frontend/react/src/views/settings/ExtensionsPanel.tsx) · [Radio decision](../adrs/0003-radio-is-a-separate-per-device-surface.md) |
| Metadata, discovery, and interoperability | The project ships adapters for catalog search, metadata enrichment, playlist sync, and export. Some clients also offer explicit links to external services. | Those integrations have distinct inputs and permissions. A future discovery extension would need pagination, public recording identity, and attribution. [Integration boundaries](download-engines.md#other-integration-seams) · [Metadata decision](../adrs/0012-catalog-metadata-and-discovery.md) |
| Project publishing | CI and distribution use GitHub and GHCR for official builds. Extension image references are digest-pinned and can point to any supported registry. The landing build can run on a static host. | The project's release pipeline and a room's extension source are independent choices. [Image publishing](release-images.md) · [Catalog setup](download-engines.md) · [Portable landing](landing.md#publish-to-a-static-host) |

The acquisition and sharing paths contain no provider-specific downloader. Older architecture records now describe the signed extension boundary. The UI test that mentions retired providers checks that those names stay out of the public landing page.
